# Правила объединения Outbound при обновлении подписок

Статус: согласовано для будущей реализации команды `xkeen-sub update`. Этот документ фиксирует поведение, но сам по себе не означает, что применение обновлений уже реализовано.

## 1. Источники подключений

При обновлении формируется итоговый рабочий массив `outbounds` из:
- подключений всех успешно обработанных подписок;
- пользовательских подключений, уже находящихся в рабочем Outbound.

Подключения подписок получают Tag с префиксом их идентификатора:
- `sub1--<исходный Tag>`;
- `sub2--<исходный Tag>`;
- далее по номеру подписки.

Префикс `subN--` означает, что подключение принадлежит соответствующей подписке и управляется обновлением этой подписки.

## 2. Определение пользовательских подключений

Рабочий Outbound анализируется по Tag:
- Tag, начинающийся с префикса `subN--`, считается подписочным подключением;
- Tag без такого префикса считается пользовательским подключением.

Пользовательские подключения нельзя удалять только потому, что их нет в загруженных подписках.

## 3. Сопоставление пользовательских подключений с подписками

Для каждого пользовательского подключения дополнительно проверяется название подключения (исходная часть Tag без подписочного префикса) на совпадение с подключением из обрабатываемой подписки.

Если название совпало, сравниваются все параметры двух Outbound, кроме Tag:
- **Название совпало и параметры совпали:** пользовательское подключение заменяется соответствующим подключением из подписки. Перед заменой исходный пользовательский Outbound сохраняется в накопительном архиве `old-user-outbound.json`. Пользователю выводится сообщение, что найдено пользовательское подключение, присутствующее в подписке, оно заменено, а исходная версия сохранена с указанием пути к архиву.
- **Название совпало, но параметры различаются:** пользовательское подключение остаётся в рабочем Outbound без изменений. Оно не перезаписывается подключением из подписки.
- **Название не совпало:** пользовательское подключение остаётся в рабочем Outbound без изменений.

При сравнении параметров Tag не учитывается: Tag используется для идентификации и размещения подключения, а не как параметр самого подключения.

## 4. Архив пользовательских подключений

Архив хранится по пути:

`/opt/etc/xkeen-sub/old-user-outbound.json`

Правила архива:
- архив накопительный;
- новые сохранённые Outbound добавляются к существующим записям;
- ранее сохранённые записи не удаляются и не перезаписываются;
- одно и то же подключение не добавляется повторно;
- исходный пользовательский Outbound сохраняется целиком, со всеми полями и параметрами.

## 5. Порядок итогового рабочего Outbound

Итоговый массив `outbounds` всегда формируется в следующем порядке:

1. Все подключения `sub1`.
2. Все подключения `sub2`.
3. Подключения остальных подписок по возрастанию номера `subN`.
4. Все пользовательские подключения.

Таким образом, подписочные подключения находятся в начале рабочего массива и сгруппированы по номеру подписки. Пользовательские подключения сохраняются в том же рабочем массиве и располагаются после всех подписочных.

При обновлении одной подписки подключения остальных подписок и пользовательские подключения должны сохраняться; обновляется только группа выбранной подписки, после чего общий порядок групп поддерживается по возрастанию `subN`.

## 6. Синхронизация Observatory

Только после формирования окончательного рабочего массива `outbounds` программа получает из него Tag всех подключений.

Полученный массив Tag целиком записывается в `observatory.subjectSelector`:
- включаются Tag подключений всех подписок;
- включаются Tag пользовательских подключений;
- порядок Tag соответствует порядку подключений в итоговом рабочем Outbound;
- источником данных является именно итоговый рабочий Outbound, а не отдельные файлы подписок.

Параметры шаблона Observatory, согласованные для новой установки:
- `probeUrl`: `https://www.google.com/generate_204`;
- `probeInterval`: `60s`;
- `enableConcurrency`: `true`.

При синхронизации обновляется `subjectSelector`; остальные пользовательские параметры существующего объекта Observatory должны сохраняться.

## 7. Синхронизация балансировщиков

Балансировщики находятся в объекте `routing`, в массиве `routing.balancers`. При обновлении используются следующие правила:

1. Программа ищет объект `routing` и массив `balancers`.
2. Если `routing` или `balancers` отсутствует либо массив `balancers` пуст, обновление завершается с ошибкой.
3. Проверяются **все** балансировщики в массиве.
4. У каждого балансировщика обязательно должно присутствовать поле `selector`, причём его значение должно быть массивом. Если поле отсутствует или имеет другой тип, обновление завершается с ошибкой.
5. Проверяется стратегия каждого балансировщика:
   - `random` и `roundRobin` могут работать без Observatory;
   - `leastPing` и `leastLoad` требуют наличия `observatory` или `burstObservatory` в конфигурации Xray;
   - неизвестная стратегия считается ошибкой;
   - если `strategy` или `strategy.type` не заданы, используется значение по умолчанию Xray — `random`.
6. Если хотя бы один балансировщик не прошёл проверку, обновление полностью прерывается с ошибкой. Ни один `selector` не изменяется.
7. Если все проверки пройдены, поле `selector` **каждого** балансировщика заменяется одним и тем же итоговым массивом Tag, сформированным из рабочего `outbounds`.

Остальные поля балансировщиков, включая `tag`, `strategy`, `fallbackTag` и настройки стратегии, сохраняются без изменений.

Проверка выполняется до записи конфигурационных файлов, обновления baseline и применения изменений. Ошибка на этом этапе не должна оставлять частично обновлённую конфигурацию.

## 8. Последовательность действий

1. Получить результаты загрузки и сравнения подписок.
2. Прочитать текущий рабочий Outbound.
3. Разделить существующие Outbound на подписочные (`subN--`) и пользовательские.
4. Обновить группы подключений успешно обработанных подписок.
5. Сопоставить пользовательские подключения с подключениями подписок по названию и параметрам.
6. При полном совпадении сохранить исходный пользовательский Outbound в архив и заменить его подписочным; при различии параметров оставить пользовательский Outbound.
7. Сформировать итоговый массив: подписки по возрастанию номера, затем пользовательские подключения.
8. Получить Tag из итогового массива.
9. Подготовить обновление `observatory.subjectSelector` и проверить все балансировщики по правилам раздела 7; для всех прошедших проверку балансировщиков подготовить одинаковый `selector`.
10. Перед применением проверить итоговую конфигурацию Xray и использовать согласованные механизмы резервного копирования и отката.

## 9. Сообщение пользователю

При замене пользовательского подключения выводится сообщение следующего смысла:

`Найдено пользовательское подключение, которое присутствует в подписке. Подключение заменено. Исходное пользовательское подключение сохранено в файле: /opt/etc/xkeen-sub/old-user-outbound.json`

## 10. Текущий статус реализации

- Загрузка подписок и сравнение Outbound реализованы.
- Подготовка результатов обновления реализована отдельно.
- Добавлен и зарегистрирован модуль `src/balancer.rs` с проверкой всех балансировщиков и атомарной заменой их `selector` в переданном JSON-документе.
- Модуль содержит тесты на отсутствие `routing`/`balancers`/`selector`, пустой массив, несовместимые и неизвестные стратегии, а также на отсутствие частичных изменений при ошибке.
- Команда `update` ещё не подключена к CLI. Чтение всех действующих конфигурационных файлов, вызов модуля в полном конвейере обновления, запись конфигураций, backup, применение и rollback остаются отдельными этапами.
