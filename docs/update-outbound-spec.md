# Спецификация контрольного запуска update

Статус: бизнес-логика согласована; часть функций реализована в режиме предварительного просмотра. Запись конфигураций, baseline и архива не выполняется.

## 1. Состояния Outbound

- Рабочий Outbound (Working Outbound) — текущий массив из действующего 04_outbounds.json. В процессе подготовки не изменяется.
- Обновлённый Outbound (Updated Outbound) — полные группы подписок, в которых обнаружены изменения после сравнения с baseline.
- Итоговый Outbound (Final Outbound) — подготовленный массив из новых групп изменившихся подписок, прежних групп остальных подписок и пользовательских подключений. Он существует только в памяти до отдельного этапа применения.

## 2. Загрузка и сравнение подписок

1. xkeen-sub update обрабатывает все подписки по возрастанию subN.
2. xkeen-sub update subN обрабатывает только выбранную подписку. Остальные подписки не скачиваются.
3. Для каждой выбранной подписки загружается содержимое по URL из sub.json.
4. Содержимое сравнивается с baseline этой подписки.
5. Если изменений нет, подписка не передаётся в Обновлённый Outbound. Её группа остаётся из Рабочего Outbound.
6. Если обнаружено хотя бы одно изменение, в Обновлённый Outbound передаётся вся подписка целиком, а не только изменившиеся подключения.
7. Если загрузка, чтение baseline или обработка завершились ошибкой, старая группа подписки сохраняется.
8. Ошибка одной подписки не останавливает обработку остальных.
9. Если ни одна подписка не была успешно загружена, выполняется отдельная проверка интернет-соединения. Если ни одна подписка не прошла обработку, дальнейшая подготовка прекращается.
10. В текущей реализации загрузка ожидает JSON-документ Xray с массивом outbounds. Конвертация Base64, URI-ссылок и других форматов подписок ещё не реализована.

### Baseline

Baseline хранится отдельно для каждой подписки в /opt/etc/xkeen-sub/:

- с названием: subN--ИМЯ.json, например sub1--Germany.json;
- без названия: subN--.json, например sub2--.json.

Baseline содержит исходный документ полученной подписки, а не объединённый рабочий Outbound. В контрольном запуске baseline только читается. Новый baseline лишь включается в план и может быть записан после будущего успешного применения. При ошибке подписки или отсутствии изменений baseline не обновляется.

## 3. Tag подписок и порядок групп

Tag формируется добавлением subscription.prefix к исходному Tag:

- с названием: subN--NAME--ORIGINAL_TAG;
- без названия: subN--ORIGINAL_TAG.

Tag, начинающийся с subN--, считается принадлежащим подписке. Остальные Tag считаются пользовательскими.

При сравнении параметров Outbound поле tag исключается.

Итоговый порядок:

1. Группа sub1.
2. Группа sub2.
3. Остальные группы subN по возрастанию номера.
4. Пользовательские подключения.

Внутри групп сохраняется порядок подключений исходного массива.

Если подписка изменилась, её старая группа из Рабочего Outbound заменяется целиком новой группой. Если подписка не изменилась, завершилась ошибкой или не выбрана для обновления, её старая группа сохраняется.

## 4. Пользовательские подключения

Для каждого пользовательского Outbound сравнивается исходное имя Tag с исходным Tag подключения из изменившейся подписки. При совпадении имени сравниваются параметры без tag.

- Имя и параметры совпали: пользовательское подключение исключается из Итогового Outbound в пользу версии из подписки. Исходный пользовательский Outbound добавляется в архив.
- Имя совпало, параметры различаются: пользовательский Outbound сохраняется, подписочное подключение также добавляется.
- Имя не совпало: пользовательский Outbound сохраняется.

Архив: /opt/etc/xkeen-sub/old-user-outbound.json.

Архив накопительный. Исходный Outbound сохраняется целиком. Если Tag уже есть и параметры идентичны, повторная запись не нужна. Если Tag есть, но параметры отличаются, создаётся следующий свободный Tag вида ORIGINAL_TAG--N, начиная с --1.

В контрольном запуске архив только читается и рассчитывается в памяти. Запись не выполняется.

## 5. Балансировщики и routing

Балансировщики находятся в routing.balancers. Фиксированный Tag балансировщика программы: xkeen-sub-balancer.

Для заполнения selector используется список Tag Итогового Outbound. Для анализа routing rules и существующего selector используется Рабочий Outbound.

### Случай 1 — балансировщики отсутствуют

1. Создаётся балансировщик с Tag xkeen-sub-balancer.
2. Его selector заполняется всеми Tag Итогового Outbound.
3. Для каждого routing.rules[].outboundTag ищется соответствующий Outbound в Рабочем Outbound.
4. Если найденный Outbound имеет протокол freedom, blackhole, dns или loopback, правило не меняется.
5. Также не меняется правило, ссылающееся на Tag, указанный в api.tag.
6. Все остальные outboundTag заменяются на balancerTag: xkeen-sub-balancer. Если соответствующий Outbound не найден, ссылка всё равно заменяется.
7. Прочие поля правил сохраняются.

### Случай 2 — один существующий балансировщик

1. Если среди балансировщиков уже есть xkeen-sub-balancer, обновляется его selector.
2. Иначе проверяется selector единственного существующего балансировщика.
3. Если в selector присутствуют все Tag Рабочего Outbound, он подходит для обновления. Дополнительные Tag в selector допустимы. Его selector заменяется всеми Tag Итогового Outbound.
4. Если хотя бы одного Tag Рабочего Outbound нет, существующий балансировщик не меняется, добавляется новый xkeen-sub-balancer.
5. routing.rules не изменяются.

### Случай 3 — несколько существующих балансировщиков

1. Существующие пользовательские балансировщики и routing.rules не изменяются.
2. Если xkeen-sub-balancer уже существует, обновляется только его selector.
3. Если его нет, добавляется новый балансировщик с этим Tag и selector из Итогового Outbound.

### Общие правила

- Все остальные параметры существующих балансировщиков сохраняются.
- Если создаётся новый балансировщик, используется стратегия Xray leastPing.
- Служебные протоколы определяются по полю protocol, а не по имени Tag.
- Список защищённых протоколов окончательный: freedom, blackhole, dns, loopback.
- Tag из api.tag защищается отдельно.
- Если в случаях 2 или 3 добавлен новый балансировщик, routing rule для него автоматически не создаётся: пользователь настраивает его самостоятельно.
- Уведомление о создании балансировщика выводится только после будущего успешного применения. В случае 1 текст сообщает, что балансировщик не был найден и создан с Tag xkeen-sub-balancer. В случаях 2 и 3 сообщается о дополнительном балансировщике и необходимости самостоятельно настроить routing rule.

Строковое значение стратегии leastPing соответствует регистру, используемому в актуальной схеме Xray: https://github.com/XTLS/Xray-docs-next/blob/main/docs/ru/config/routing.md

## 6. Observatory

После формирования Итогового Outbound извлекаются все его Tag в том же порядке, что и Outbound.

Массив целиком записывается в observatory.subjectSelector или burstObservatory.subjectSelector. Остальные параметры объектов Observatory сохраняются. Если конфигурация Observatory не найдена, подготовка завершается ошибкой; автоматическое создание объекта в рамках update не выполняется.

## 7. Проверки

- Проверяется структура документов и массива Outbound.
- Проверяется наличие и уникальность Tag Итогового Outbound.
- Проверяются ссылки balancerTag.
- Итоговая проверка xray run -test -format=json запускается во всех режимах validation.
- on: ошибка проверки помечает план как запрещённый к применению.
- alert: ошибка выводится как предупреждение.
- off: отключает только предварительные проверки отдельных Outbound; итоговая проверка Xray остаётся обязательной.
- Xray config test не подтверждает доступность удалённых серверов.

Проверка Xray запускается с временными копиями подготовленных конфигураций в системном временном каталоге. Активный каталог /opt/etc/xray/configs открывается только для чтения. Временные копии удаляются после проверки.

Итоговая конфигурация, отклонённая Xray, не может быть применена ни в одном режиме. Предварительная проверка отдельных Outbound и цикл автоматического исключения проблемных Outbound по диагностике Xray пока не реализованы. На текущем этапе режим validation влияет на оформление результата итоговой проверки.

## 8. Контрольный запуск и ограничения

Команды:

- xkeen-sub update — контрольный запуск для всех подписок.
- xkeen-sub update subN — контрольный запуск одной подписки.

Контрольный запуск:
- скачивает и сравнивает подписки;
- формирует Обновлённый и Итоговый Outbound;
- рассчитывает архивируемые пользовательские подключения;
- готовит routing и Observatory;
- запускает предусмотренные проверки;
- выводит полный подготовленный JSON и отчёты;
- не записывает 04_outbounds.json, routing, Observatory, архив или baseline;
- не применяет конфигурацию и не перезапускает Xray.

Резервное копирование, откат и применение конфигурации исключены из текущего этапа и будут прорабатываться отдельно.

## 9. Статус реализации

Реализовано в контрольном режиме:
- загрузка и сравнение JSON-подписок;
- построение полных групп изменившихся подписок;
- сохранение старых групп неизменившихся и неуспешных подписок;
- разделение подписочных и пользовательских Outbound;
- сравнение пользовательских подключений и расчёт архива;
- подготовка Итогового Outbound;
- три согласованных сценария балансировщиков;
- синхронизация Observatory;
- подготовка временных копий конфигураций для Xray config test;
- вывод плана без изменения действующих файлов.

Не реализовано:
- конвертация не-JSON форматов подписок в Xray JSON;
- автоматическое исключение проблемных Outbound по диагностике Xray;
- применение подготовленных конфигураций;
- запись архива и baseline;
- резервное копирование и откат.
